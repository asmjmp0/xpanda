# AGENTS.md

This file provides working guidance for AI coding agents in this repository.

## What This Project Is

**xpanda** — a HarmonyOS `.abc` (Panda / ArkCompiler bytecode) decompiler, implemented in **pure TypeScript** (Node.js ≥ 18). Supports bytecode version `24.0.0.0` (backward compatible with 13.0.1.0). The repo is an npm workspaces monorepo split into four sub-projects: `xpanda-core` (core library), `xpanda-cli` (command line), `xpanda-mcp` (MCP Server), and `xpanda-web` (browser UI, React + Vite, pure frontend), all under `packages/`; cli/mcp/web depend on the core library via the package name `xpanda-core`. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for architecture details.

## Skills

Repo-local agent skills live in `.agents/skills/<name>/SKILL.md`. **Load the matching skill before starting the task** — use the `skill` tool with the id from the skill's `name` frontmatter field, and follow its workflow instead of improvising.

| Skill | Use when |
|---|---|
| `.agents/skills/xpanda-structure-forensics/` | Decompiled output for a class is structurally wrong or missing — a vanished try/catch/finally, a continuation duplicated into a catch, a dropped catch body, a wrong loop shape, code only reachable from an exception path that is absent, or a "why is this not restored" report pointing at a line of output. |
| `.agents/skills/xpanda-try-restore-survey/` | Auditing a whole `.abc`/`.hap` sample for how many try/catch/finally structures are restored vs lost ("how many finallys are not restored in this abc", release-quality check of a new sample, sample-wide vs isolated bug triage). Cross-checks the bytecode try table against the decompiled output; exit code 1 on findings. |

Each skill directory may ship its own helper scripts (e.g. `scripts/abc-inspect.ts`, run with `npx tsx`); read the skill's `SKILL.md` first, since it documents how they are meant to be used. When adding a new skill, put it under `.agents/skills/<name>/` with the same `SKILL.md` layout and add a row to this table.

## Hard Rules

1. **`packages/xpanda-core/src/disasm/opcodes.ts` is generated; do not hand-edit** — it is generated from `packages/xpanda-core/resources/isa.yaml` by `npm run gen:opcodes`.
2. File format parsing, instruction kind mapping, handle behavior, and structured reduction order must stay deterministic; validate changes with the `md5.abc` / `class.abc` test snapshots.
3. Write comments and documentation in English, keeping the existing style (class header `@Author: jmp0`).
4. Do not introduce CI configuration or change the dependency structure unless the user asks.
5. Optimizer passes return a `boolean` indicating whether the AST was modified; `SimplifyExport` runs fixed-point iteration. Do not keep procedural logs inside passes.
6. **Per-class output must be a pure function of that class**: do not introduce cross-class mutable state (global counters, mutable caches shared by offset, etc.), otherwise `-j` parallel output diverges from serial. Generated-name counters reset per class in `PandaDecompiler.decompileRaw()`; `packages/xpanda-cli/test/parallel-consistency.test.ts` has the serial/parallel consistency regression.
7. **Cross-package imports always go through package names**: cli / mcp may only import the core library via `import ... from "xpanda-core"` (single entry `src/index.ts`); no deep relative paths. core must not depend back on cli / mcp. **core must stay browser-safe**: no Node built-in modules (fs / path / os / zlib / worker_threads / Buffer, etc.) inside the import closure of the single entry, no disk IO, no workers — disk IO is implemented by cli / mcp's own `src/io.ts`, and the parallel simplify worker pool lives in xpanda-cli's `src/parallel/`.
8. **Only run `git commit` when the user explicitly asks for it.** Editing files, running tests, and reporting results never imply a commit; leave changes in the working tree.
9. **Bump the affected package versions before every commit.** Before running `git commit`, raise the `version` field in every workspace `package.json` whose package is changed by that commit — `packages/xpanda-core`, `xpanda-cli`, `xpanda-mcp`, `xpanda-web` — using semver: new feature → minor, bug fix / internal compatibility fix → patch, breaking change → major. Bump the root `package.json` together with `xpanda-core` (the root version mirrors core). Use `npm version <version> --no-git-tag-version [--workspace <name>]` (or edit `package.json` and keep the lockfile consistent), and never create git tags automatically. A commit that only touches repository-level docs (`README*`, `AGENTS.md`, `docs/`) may skip version bumps unless the user asks.

## How To Do Common Tasks

### Add/modify a bytecode instruction

1. Check that the instruction exists in `packages/xpanda-core/resources/isa.yaml`; if not, update it and run `npm run gen:opcodes`;
2. Register the semantic kind in `KIND_MAP` / `classifyKind` in `packages/xpanda-core/src/disasm/PandaInstruction.ts` (don't forget the `InstructionKind` union);
3. If it needs dedicated semantic fields, parse them in the `PandaInstruction` constructor switch;
4. Implement a handle for that kind in `HANDLES` in `packages/xpanda-core/src/decompiler/MethodHandler.ts` (follow the existing handles' style);
5. `npm test`.

### Add a simplify pass

1. Implement `ISimplify` in `packages/xpanda-core/src/simplify/`;
2. Register it in `SimplifyExport.ts` (regular passes go into the `simplifyALL` array; global passes go at the pipeline head/tail, e.g. `CallResultSimplify`, `HighLevelGrammarSimplify`);
3. Only passes that need to run repeatedly in the fixed-point iteration go into `simplifyALL`; one-shot finishing steps (e.g. `TempVariableSimplify.foldConditionAssignments`, `SyntaxRewriteSimplify.hoistTestPrefixes`, `TailMergeSimplify`, `TempVariableSimplify.cleanupDeadStores`) are called directly at the end of `SimplifyExport.simplify()`;
4. Run `npm test` and confirm the snapshot changes are expected.

### Upgrade the supported bytecode version

Replace `packages/xpanda-core/resources/isa.yaml` → `npm run gen:opcodes` → add kind/semantic parsing for new instructions in `PandaInstruction.ts` → add handles in `MethodHandler.ts` → adjust format differences in `packages/xpanda-core/src/file/desc/Header.ts` etc. → `npm test` + large-sample verification.

### Modify file format parsing

The corresponding classes are in `packages/xpanda-core/src/file/`; preserve format semantics such as offset masks, cache semantics, and bounds handling. Verify with `md5.abc`, `class.abc`, and `zhihupp0.59.hap` afterwards.

### Modify the optimizer

- Copy propagation must cap expression size / clone budget to avoid `v2 = v1 + v1; v3 = v2 + v2; ...` exponential blowup;
- Cleanup of inactive variables, SequenceExpressions, return statements, and catch parameters must go through liveness / scope checks;
- **Capture detection must look at both `binding.referencePaths` and `binding.constantViolations`.** Outer variables that are "write-only" in a closure appear only in constantViolations; looking only at reads would treat the outer initialization (e.g. `local_1_1 = undefined`) as the only value, propagate it to reads after the closure, and delete the declaration;
- **Name-level liveness cannot tell old and new versions of a temp apart**: for `X = RHS` where RHS reads X exactly once, that read is the last use of the old value (`acc = p0.trim(); acc = acc.length` → `acc = p0.trim().length`). If the name is still live after the statement (later reads see the new value), a non-copyable right-hand side may only be moved into a call receiver position (`v0 = !v0.test(p0)`); the bare member load `acc = acc.test` is an intermediate form AccCallSimplify depends on — inlining it early would make `acc.call(recv, ...)` unrestorable;
- **Self-read member chains `X = X.prop; X = f(X)` → `X = f(X.prop)`** (`foldSelfReadChains`): the RHS of `X = X.prop` reads the old value, so copy propagation won't cache such expressions; if its result is consumed exactly once by the immediately following assignment, the whole expression can be moved between the two assignments. Requires A to be a pure member load, B to read X exactly once, and B to not write X or any name A depends on;
- **Self-update then single read `X = F(X); C` → `C[X := F(X)]`** (`foldSelfUpdateIntoNextRead`, in the fixed-point pass before copy propagation): the ternary lowering `nl >= 0 ? value.slice(nl + 1) : ''` leaves `nl = nl + 1` as a statement before the value assignment, which prevents `HighLevelGrammarSimplify` from synthesizing the ternary (branches must be a single assignment). Requires F to be pure, `X = F(X)` to be a binary/unary expression (not a member load — `X = X.method` is the AccCallSimplify method-quantity form), X to be read exactly once in F and once in the consumer, X dead after the consumer (`liveAfter`), and no name F depends on to be written by the consumer. `acc` is excluded (it has its own materialization pipeline), and a preceding write to X means the shape is an accumulator chain (`X = E; X = X op F`) for `foldAccumulatorChains`;
- **Accumulator chains are not limited to binary ops** (`tryFoldAccumulatorPair`): member-call/member-load chains like `X = E; X = X.trim()` / `X = X.length` also read the old value exactly once. When the read lands in the leftmost evaluation position (call receiver / member object), E may contain calls; otherwise E must be pure (evaluation order would jump over E's side effects); keep checks like `countReadsInNode === 1` and `hasDeferredSelfReference`;
- **Hub alias folding must redirect reads of the old value too** (`tryFoldTempAlias` + `redirectReadsUntilWrite`): in `acc = E; v5 = acc; <reads of acc>...; acc = G`, all reads between `v5 = acc` and the next write to acc belong to the old value; retarget them to v5 first, then move E into v5. Give up on conditional writes in branches/loops/exception paths (or writes to the target) to avoid treating post-write values as old values. Member targets (`v0.sbox = acc`) are not redirected;
- **Unfold else when the then branch always exits** (`SyntaxRewriteSimplify.flattenElseAfterExit`): `if (C) { return/throw/break/continue } else { BODY }` → `if (C) { ... } BODY`. Must run after HighLevelGrammarSimplify's ternary synthesis (if/else whose two branches are both a single return must first synthesize into a ternary, otherwise it gets torn apart), and only unfold inside statement lists (when a LabeledStatement directly wraps the if, break label depends on else staying inside the label); conservatively skip when the else block's top level has block-scoped declarations (let/const/class/function);
- **Fold boolean materialization of nested if / else-if bottom-up**: `if (!p2) { if (!f) acc = true else acc = false } else if (!g) acc = true else acc = false` should fold to `if (p2 ? !g : !f)`. `HighLevelGrammarSimplify`'s IfStatement folding uses `exit` to guarantee the inner if becomes an assignment statement first; return chains are not folded into nested ternaries, keep the `else if ... else` structure;
- **`foldShortCircuitChains` folds the `X = E; if (X/!X) { X = B; }` materialization chain into `X = E &&/|| B`** (when the test was re-materialized into the original expression by structured reduction, E must be pure). The negated form with an empty then, `if (X) {} else X = B`, is equivalent to `if (!X) { X = B }`; fold it as `X = E || B` with flipped polarity (give up when the then is non-empty or has multiple statements; only look at else when `isEmptyBranch` holds); chains starting with the self-negation `X = !X` must be skipped: the parity of the whole negation chain belongs to the tail `foldConditionAssignments`, and eating the chain head early would prevent `X = has(); X = !X; if (!X) { X = set() }` from folding back to `if (!has())`. **The chain head may also be a negated-test self-assignment** (`TestFolds.foldNegatedTestSelfAssignment`): the compiler lowers `X = A && B` — when X already holds B — to `if (!A) { X = A }`; it is exactly equivalent to `X = A && X` (A falsy writes A back, A truthy keeps X), and only after this rewrite can the following `if (X) { X = C }` chain start folding. Require A to be pure (the original evaluates it in the test and again in the branch), X to be an uncaptured temp, the branch value to be structurally equal to A, and the next statement to test X; an isolated `if (!A) { X = A }` is left alone;
- **`X = E; <statements not touching X>; if (C) { X = F }` folds to `X = C ? F : E`** (`HighLevelGrammarSimplify.checkAndTransformToConditionalAssignment`): ArkTS lowers an object field default (`topInsetVp: immersiveReading ? 0 : OFFSET`) into `v0 = 0` before the object literal, then `if (!immersiveReading) v0 = OFFSET` after it, then `obj.topInsetVp = v0`; the object literal construction is what sits between the assignment and the if. Requires E to be pure (it moves from before the if into the ternary's else branch), the skipped statements and C not to read/write X, C/F not to read X (the ternary evaluates the test/branches before assigning X, so they would see the old value), and the test not to be a `LogicalExpression`. Skip when C is structurally equal to E or its complement (comparison/unary `!` negation): that is the short-circuit chain `X = E; if (X/!X) { X = B }` for `foldShortCircuitChains`, and grabbing it as a ternary would leave `return acc ? B : acc` behind. The tail `ObjectLiteralSimplify` run then merges the field and the literal into `return {...}` / the call argument;
- **Impure expressions (`call` / `new` / functions/classes) may only move on a true last read**; when both the if's test and branch bodies read the same temp, don't move it, otherwise the call gets duplicated. **Exception**: when the read is in the if's test and both branches definitely overwrite the variable before reading it (`definitelyWritesBeforeRead`), the old value is dead after the test and may move into the test (`v0 = new RegExp(...); if (!v0.test(p0)) {...} else {...}` → `if (!new RegExp(...).test(p0))`);
- `acc = !acc` can come from `callruntime.isfalse` or from condition materialization (`istrue + jnez + ldtrue/ldfalse`); fold by the parity of the negation count, don't just strip one layer;
- Self-negation chains in test sequences (`if (A || (X = E, X = !X, !X))`) only fold when X is dead after the test, has no other reads outside the test, and branches/prefix don't read-then-write; self-negation inside loop tests is not handled yet (dead store cleanup and accumulator chain folding in loop tests are `foldLoopTestTemps`'s job, see next bullet);
- **Loop tests are expression sequences; `cleanupStatements` can't see them**: `foldLoopTestTemps` does liveness analysis in the test's own evaluation order, deleting dead stores (`acc = !(acc !== undefined)`, register restores like `v8 = false`) and folding `X = E; X = F(X)` into `X = F(E)`, `X = E; Y = X` into `Y = E`. The live set after the test must be the loop body entry live set (`loopBodyIn`, recorded by the liveness fixed-point iteration) ∪ live-after-loop (`liveAfter`): temps written-then-read inside the body (`v8.done` after `v8 = v6.call(v5)`) must not count as live uses of the test's writes; looking only at `liveAfter` would wrongly treat `v8 = false` as live;
- **A do-while's test evaluates after the body**: liveness must remove test reads where "the body definitely writes X before reading" from the loop-entry live set, otherwise `X = !E; if (!X)` won't fold (X still looks live in the loop) or would duplicate evaluation after folding. `foldDoWhileTestAssignments` then folds `do { ...; X = E } while (!X)` into `while (!E)`, requiring X dead after the loop and no `continue` in the body;
- Constant prefix hoisting like `if (A || (v1 = 0, v2 = 2, B))` (`hoistTestPrefixes`) requires: the prefix is only temps assigned constants, the short-circuit branch directly returns/throws and doesn't read those temps, and not being inside a `try` with `finally`;
- `ObjectLiteralSimplify` merges the `createobjectwithbuffer` template object with adjacent `obj.key = value`: requires assignment order to match the template's field order, and the object not captured by closures. Unassigned fields at or after the first merged field must still hold literals (so moving the new assignments into the literal cannot reorder side effects); fields before it may already hold real expressions from an earlier merge round. `obj = {...}; return obj` inlines into `return {...}`, and a single following read (`rows.push(obj)`, `f(obj)`) inlines the literal there too, as long as `canDeferTestValue` says the evaluation order is preserved and all other reads happen before the object is built. It also runs again at the tail after `TailMergeSimplify`: fields whose value only becomes a plain `obj.k = <expr>` at the tail (the `v0 = C ? A : B` computation folded away by `foldNextReadAssignments`) merge then. Function-valued fields merge like any other value (aes's `cipher` / `subBytes` methods), so the "does the RHS reference the object" check must be **binding-aware**: a method body usually declares its own `let v0` temp, and a plain name scan would treat those shadowed locals as references and keep every method as `obj.cipher = function ...`. Use the outer binding's scope resolution (`p.scope.getBinding(name) === outer`), not `referencesNameDeep`, whenever the value contains a nested function. Function properties in object literals are created in original evaluation order and are not hoisted;
- `HighLevelGrammarSimplify` synthesizes `if (x === null || x === undefined) x = default` into a switch; `NullishCoalescingSimplify` at the pipeline tail restores `v = obj.k; switch (obj.k) { case null: case undefined: v = default; }` into `v = obj.k ?? default`. Merging the two evaluations is only allowed when the discriminant is a pure member expression;
- **`??` also appears without any switch**: `X = E; if (X == null) { X = D }` and the equivalent `if (X != null) … else { X = D }`, `X === null || X === undefined` (NullishCoalescingSimplify runs before normalizeConditionTests merges the strict pair), and the ternary form `X == null ? D : X` are folded by `NullishCoalescingSimplify` into `X = E ?? D` / `E ?? D`. The `if` form requires the assignment to be the immediately preceding statement, the branch to contain exactly one `X = D` (the other branch empty or an `X = X` self-assignment), the discriminant to be either the temp itself or an expression structurally equal to `E` (pure), and `D` must not read `X` — in `X = E ?? D` the right operand is evaluated before `X` is assigned, so it would see the pre-statement value. It runs before `foldReturnAssignments`, so `X = E ?? D; return X` still folds to `return E ?? D`. This is what restores `return v8?.runs ?? []` in `MusicSearchService.getMusicDescriptionRuns` and the `cookieProvider?.getCookies() ?? []` fallback in `ZhihuHttpClient` (where the assignment used to be dropped entirely);
- **Switch synthesis must split out every term of the `||` test**: unrecognized terms (e.g. `!(a !== b)`, conditions with sequences) must not be silently dropped, otherwise you generate a switch that misses conditions. When the chain tail can't be split, only put the current if and its else chain wholesale into `default` (`partial`); if the very first condition can't be split, don't synthesize. **The last source case is often lowered as a default-branch guard hoisted into the else block** — `else { if (disc !== VALUE) EXIT; BODY }` — which is `else if (disc === VALUE) { BODY } else { EXIT }` (`extractTrailingGuardCase`); without this normalization the chain only exposes two `===` labels and stays an if/else-if. Only `!==` / `!(disc === VALUE)` are accepted (switch cases use strict comparison), EXIT must end in `return`/`throw` (a bare `break` would be captured by the switch) and BODY must be non-empty. The guard descriptors are plain nodes, and the new case block is only used if the whole chain really becomes a switch (the ≥3-label and same-discriminant checks still apply);
- **A for-of with early return lowered to `do { vv = it.next(); if (vv.done) { DONE } ...; acc = T } while (acc)` + `it.return()` cleanup is restored by `checkAndTransformDoWhileToForOfStatement`**: the loop test becomes `if (!T) return E` at the end of the for-of body, and `DONE` (the loop-exhausted path, which must exit on every path) moves after the for-of. `E` need not be a constant but must be pure and must not read the iterator (`v16.content` in `extractSubscriberText`); the boolean-literal form `if (vv.done) return true` / `return false` is just the `DONE`/`E` special case. Also requires `it` no longer read/assigned outside close (a reused temp iterator is fine when a newer `it = ...` writes before the read — `hasNewerValueBefore` / `hasPriorAssignmentInAncestors`), no break in the body, `DONE` writing `vv` before reading it (after the for-of `vv` holds the last element, not the done result object), and continue appearing only as `if (acc) continue` or as `acc = G; if (G) continue` (both guarantee the test is true on continue paths, so skipping the extra exit check is equivalent). The hoisted `it.next` lowering (`F = it.next; vv = F.call(it)`) is normalized first (`foldHoistedIteratorNext` now also accepts do-while and tolerates temps reused earlier in the function as long as the deleted value isn't observable), and a pre-loop `acc = <literal>` test init is dropped — it is never read by a do-while, and leaving it would overwrite the iterable expression the for-of head still evaluates (`acc = false; for (v of acc)`). The transform runs top-down (outer loop first) with a rescan, because the done branch — and any nested iterator loop inside it — is moved after the loop and leaves the traversal queue. The same function also restores the **break** form, `for (const x of xs) { ...; if (T) { A = x; break; } }`: here the statements after the loop are `EXIT` (the break-path prefix) + `close(it)` + the shared continuation, and `DONE` is a copy of that continuation, so the result is `for (const x of xs) { ...; if (!T) { EXIT; break; } }` followed by the continuation with `DONE` **discarded** (keeping it would make `break` fall into the exhausted branch). Requirements: `EXIT` is straight-line code (no declarations / break / continue / label, so moving it into the new loop branch cannot rebind anything), the continuation after `close` exists, and `DONE` always exits the function. The transform now also runs from `simplifyTail` (do-while rescan) because the close block only becomes `if (it.return != undefined)` and the test materialization only becomes `testName = T` after the tail condition folds; the loop test may be a bare identifier or a negated one (`while (!v3)`), in which case the exit test is computed by negation parity. When the loop body has no early exit at all the compiler emits **no** `close`, and `E` is the statement directly after the loop (`return E` or `throw E`, which must be the last statement of that list); a `throw new Error(...)` exit still folds to `if (!T) throw new Error(...)` because the exit expression is evaluated once on the test-false path and purity is only enforced for `return` (`new` is not a pure expression). Stale `binding.referencePaths` after `foldHoistedIteratorNext` are matched by statement, for-of/for-in loop variables count as writes (not reads), writes located after the loop are ignored, and references inside the discarded `DONE` block are skipped. The do-while test may also still be a **bare condition** (`} while (vv.id !== p1)`) after `foldDoWhileTestAssignments` folded `acc = T; } while (acc)`; there is no `testName` then, the exit test is the condition negated (`negateLoopTest` flips a comparison operator instead of emitting `!(…)`), and a `continue` is only accepted when its guard is structurally identical to the loop test. When the body has no `vv = vv.value` unpack statement the loop variable is the iterator result object throughout, so `vv.value` is the element and must be replaced in the **loop test as well** (`while (again(vv.value))` → `if (!again(vv))`); with an unpack statement `vv` is already the element and `vv.value` is the element's own property (keep it). A break-exit loop may also end with the pseudo-goto break that `virtualizeIrregularExits` emits for a goto target (`break; //from goto label_x`), with the close inlined as `{ v = hole; if (it.return != undefined) it.return(); }` and the target `label_x: ;` right after the close (`amcl1.0.6.abc`'s feature_core/t11/a12 `#*#c1268`): `DONE` is that break, the label is the shared continuation, the close block is `extras` and is removed with the label (only when the label body is an `EmptyStatement` and no other break/`xpanda_goto` targets it), and both the exhausted and break paths then fall through to the continuation. 
- **Only the await's reject dispatch may be removed from the region graph**: `RegionGraphBuilder` turns an `asyncfunctionawaituncaught` condition into a Linear region by deleting the throw successor (the `lda <await result>; throw` block that rethrows the rejection). Jumping to a throw block is not proof of a reject dispatch — the *normal* continuation may throw too (`catch (e) { …; throw e }`, amcl g9 `executeInstall`, or `await open(); …; throw new Error(…)`, sideload r9 / launch n16), and deleting it swallowed the catch's rethrow. `awaitResultRegister` reads the register stored right after `resumegenerator`, and only a successor that `throwsRegister` of exactly that register is removed.
- **`while (true) { vv = it.next(); if (vv.done) break; vv = vv.value; ... }` is restored to `for (vv of iterable)`** (`checkAndTransformToForOfStatement`): requires `it = iterable[Symbol.iterator]()`, and `it` is not read/assigned inside the body except the first `next()` (the iterator init may sit up to four `X = <literal>` statements before the `while` — `copyDirRecursive`'s `v5 = 0`, commons/w1 `y91`'s `v7 = 0` — and those assignments stay put; a done branch that `return`s or `throw`s without reading the iterator or the loop variable is moved after the for-of, which is how `e1268` loses its `while (true)`) (ArkTS inlines `it.return()` in early-return branches; after the transform `it` is no longer assigned). **That inlined close (`if (it.return != undefined) { it.return() }` immediately followed by an exiting statement) is now deleted instead of blocking the transform**: a source `for...of` closes the iterator on `return`/`throw` by itself, so the residual is redundant (only `return`/`throw` exits are accepted — `break` may belong to an outer structure, `continue` does not close). The close is removed only after every check passed, so a late bail never leaves an unclosed iterator. Because `hole` finally residue wraps the close as `if (false) {} else if (it.return != undefined) { it.return(); if (hole != hole) throw hole; }` until `foldSentinelGuards`/`removeUnreachableStatements` run at the very end of `SimplifyExport.simplify`, `restoreIteratorLoops` (the while/do-while for-of part of `simplifyTail`) is called a second time after `removeOrphanJumps` — that is what restores `amcl z12`'s `local_0_20` / `local_1_5` capability checks. The iterator init may sit a few statements before the loop when those statements are only `X = <literal>` (`copyDirRecursive`'s `v5 = 0`); they stay in place. A done branch that is `return`/`throw` of a value that does not read the iterator or `vv` (`return undefined` in `attachLegacyBundledLibraryChecks`) is moved to after the for-of. A done branch wrapped in `label_x:` whose exit reads `vv` is still left as-is. The compiler reuses the same temp iterator/loop variable across consecutive whiles, so reads outside the loop aren't categorically forbidden: it's safe as long as a new `it = ...` / `vv = ...` definitely overwrites before the read (`hasNewerValueBefore` walks the read's ancestor blocks looking for a direct assignment; reads inside closures give up immediately). After for-of ends `vv` stays at the last element, while the while form stops at the done result object, so reads after the loop must be overwritten by later assignments; reads before the loop are unaffected. Only replace `vv.value`; other objects' `.value` in the body must stay unchanged. Decompiled AST nodes have no `start/end`, so deciding whether `vv` is inside the loop uses path ancestry (`ref.findParent`), not positions; the replacement must `.traverse` on the `body` path still attached to the AST — don't build a detached `blockStatement` and traverse it separately (missing `parentPath` breaks the scope chain of nested scopes at non-`Program` nodes, and `Scope.crawl` throws `addGlobal`); `it.next()` may be preceded by pure register-copy statements (`v2 = v0`, the per-iteration save a surrounding try/catch needs); they stay at the top of the for-of body instead of being hoisted out — the catch must see the value from the start of the failing iteration.

### Modify Region Reduction / Condition Polarity

The most error-prone part of structured analysis is "should this condition be inverted":

1. **Don't rely on `regionGraph.successors()` return order**. `ValueGraph` returns in insertion order, unrelated to true/false edges; branch polarity must be decided with `edgeValueOrThrow(region, succ)`.
2. `conditionalExp` describes the fallthrough (false edge) branch condition: for jnez the false edge is `!acc`, for jeqz it's `acc`; only folding the true edge (`coalesceTailRegion`) needs `expInvert()`.
3. `simplifyConditionalSequence` merges `if (A) ... if (B) ...` into an `OrLogicalExpressionStatement` and sets `logicalRegion`; when `reduceSequence` merges such a Region it must propagate `logicalRegion`, otherwise the test can only be generated from `acc` later and the `A || B` computation is lost.
4. `Region.copy()` (irreducible Tail duplication) must preserve the `conditionalExp` / `logicalRegion` / `exceptionLandingPad` / `tryCatchHelperRegion` flags.
5. If a merged sub-region is already a `LogicalExpressionStatement` (`(A || B)` / `(A && B)`), **do not append `acc`/`!acc` again**: its expression is already the condition value; appending would overwrite the condition with the last comparison result in `acc` (`name === A || ((name === B, acc) || ...)` is both a semantic error and leaves a dead `(acc = E, !E)` assignment). `||`'s operands are jump conditions, `&&`'s operands are fallthrough conditions; invert when parent/child types differ.
6. When `virtualizeIrregularExits` hits irregular exits inside a loop body, **emit exactly one statement per edge**: conditional regions emit `if (cond) break`, linear regions emit an unconditional `break`. Emitting both yields `if (cond) break` followed by an unconditional `break`, so the body only ever runs once (`AppUpdateClient.fetchReleaseDetail`'s inner for...of once returned the iterator result object directly because of this). When the exit target is a Tail with `outDegree === 0` (only `return`/`throw` left), `break` won't do (it only jumps to the loop follow); copy the Tail's statements into that branch instead — this is exactly the case where the target has other predecessors and cannot merge.
7. **`tryCatchHelperRegion` is only valid while both try/catch branches are unconsumed**: after `reduceIfRegion` emits an `IfPandaStatement` (case 3/4) or `reduceTryCatchWithDeadBranch`, the flag must be cleared (`region.tryCatchHelperRegion = false`). Otherwise when that region keeps absorbing following code, `reduceSequence` propagates the flag all the way down, and later normal conditional regions get treated as try/catch by `IfPandaStatement`, emitting semantically wrong `try { ... } catch { success path }` statements (`HttpDownloader.request` once put its success path into catch this way).
8. **When one branch of a try/catch reduces to a Tail with `outDegree === 0` and the other is a back edge**, `reduceTryCatchWithDeadBranch` is needed: case 3 requires both branches to converge on the same successor, case 4 requires both to be Tails; when neither holds, the region graph stalls until `can not reduce the graph` (`HttpDownloader.request` / `postBinaryWithRetry` loop bodies). The continuing branch must already be reduced to `Linear` (otherwise leave it for the next fixed-point iteration), and both branches must have the current region as their only predecessor.
9. **The `&&`-merged logical region (`AndLogicalExpressionStatement`) expression is the fallthrough condition**, not the true edge condition; when folding a Tail on the true edge in `coalesceTailRegion` / `virtualizeIrregularExits`, `expInvert()` has no effect on it — use the inverted branch instead (`new IfPandaStatement(region, null, tail)`), then `normalizeConditionTests` folds it into `!A || !B`. Otherwise conditions come out inverted (`if (code && code >= 400) return` ← should be `if (!code || code < 400) return`).
10. Verify with `zhihupp0.59.hap`'s `AbsoluteUrlParser` / `ZhihuHttpClient`, `AppDestination.shouldReloadAfterAuthentication` (a 17-term `===` `||` chain), `AppUpdateClient.fetchReleaseDetail` (early return inside for...of), `yourpipe0.7.0.abc`'s `HttpDownloader.request` / `postBinaryWithRetry` (try/catch nested in the loop body), and `aes.abc`'s `Counter.increment` (must be `!== 255`).
11. **Region-graph dead code must be pruned by reachability, not only by in-degree**: ArkTS 13's finally handlers carry `codeSize === 0`, so `RegionGraphBuilder` skips them; the cleanup code downstream of such a handler has no predecessor in the region graph, but when it contains a cycle (the `for...of` close loop in `amcl1.0.6.abc`'s commons/h1/w1 `#*#w91`) its nodes keep `inDegree > 0` and survive the in-degree dead-code deletion as an island. `analysis()` only reduces from `entryRegion`, never visits the island, so the graph can't collapse to one node and the method falls back to `SimpleAnalysis` after 3000 rounds (`can not reduce the graph`). `RegionGraphBuilder.build()` therefore also prunes every region unreachable from `entryRegion` once the try/catch helper regions are wired; if the unreachable set contains a real exception landing pad the build throws instead, so the method keeps the old fallback rather than silently dropping catch semantics.
12. **The structured statement graph must never contain a cycle**: `Region.decompile()` expands region references recursively, so a region whose own statement subtree references it again recurses forever — at shallow depths it throws `RangeError` and the method falls back to `SimpleAnalysis`, at deeper nesting it exhausts the native stack/heap and kills the process. `reduceIfRegion` case 3 can create this shape when both branches converge on the condition region itself (`amcl1.0.6.abc`'s r2/l3 `#~@2>#loadLive`: the else branch embeds the 1017 body region, then `reduceCyclic` wraps the condition in a `while` and `reduceSequence` merges that same body region — which the `if` still points at — into it). Two defenses: `reduceSequence` refuses a merge when `statementsReferenceRegion(nextRegion, region)` says the merged statements would reference `region` again, and `analysis()` runs an iterative DFS (`findStructuredCycle`) before `root.decompile()` that throws `PandaDecompileException` on a remaining cycle so the method degrades instead of recursing. Keep the DFS iterative: the expanded tree can be thousands of levels deep and a recursive walk itself overflows.
13. **Logical-condition folding only accepts real condition regions** (`canMergeLogicalCondition` in `simplifyConditionalSequence`): a `TryCatchHelperRegion` has no statements — its `false` edge is the try body and its `true` edge the handler — so merging it as an operand of `A || B` / `A && B` builds a `LogicalExpressionStatement` whose `first`/`second` is `undefined` and `decompile` throws `TypeError`, degrading the whole method. The guard is needed because a helper is a `Condition` region with exactly two successors and can match the `nextDestRegion === destRegion` / `nextNextRegion === destRegion` shape (`amcl1.0.6.abc`'s n4/o8 `clearDisplayListeners`: `if (enhancedDisplays) { try { off } catch {} }`); once the helper itself reduces to a `try` statement, the enclosing `if` reduces normally through `reduceIfRegion` case 1/2.

## Pitfalls and Notes

- **Degradation paths are by design, not bugs**: single methods > 2000 basic blocks (`MAX_STRUCTURED_BLOCKS`; the stall bound `MAX_REDUCTION_ROUNDS` = 3000 is counted independently of the block count, so a large method isn't starved of reduction rounds), estimated structured expansion > `MAX_STRUCTURED_STATEMENTS` (30k statements), and unregistered instruction kinds all route the method through `SimpleAnalysis` linear output; `jeq/jne/jstricteq/jnstricteq` instructions throw on construction, and the lexical phase (`PandaLexical`) skips the method and emits a placeholder function body without interrupting the whole class.
- **`Region.decompile()` expands shared nodes by reference**: the reducer keeps a shared continuation as one `Region` referenced from several statements, and each reference is emitted again. A 164-node region graph / 205-block method can unfold into 393k statements (283MB AST) — exponential in the nesting depth of shared tails. `StructureAnalysis.estimateStructuredStatements()` estimates this unfolded size (memoized, capped) and throws above `MAX_STRUCTURED_STATEMENTS` so the method falls back to `SimpleAnalysis` instead of OOMing `simplify`. Don't raise the limit without measuring the peak heap; simplify of a 63MB AST already needs ~1.5GB.
- **A shared tail that is both the `else` of an `if` and the tail of its then-branch is redundant and is pruned before `decompile()`** (`StructureAnalysis.pruneRedundantTailBranches`): ArkTS lowers optional-field validators to `if (field === undefined) goto next; if (!valid) goto error; next: …`, which reduces to `if (C) { …; if (D) { X } else { NEXT } } else { NEXT }`. Emitting that shape duplicates `NEXT` at every nesting level, so 14–15 checks unfold into 75k/393k statements (amcl1.0.6.abc's `#*#t1359` / `#*#w1359`; pruning brings the estimate down to 451 / 310). - **`matchConditionPattern`'s compound test supports multiple reads, but only when a negation chain exists**: the compiler lowers `A && (f(), A)` ("reading the same materialized boolean") into `acc = E; acc = !acc; if (!acc && (f(), acc))`; both reads in the test must be replaced with the same parity value to eliminate `acc = !acc` (`AppUpdateClient`'s `fetchReleaseDetail` guard and `AVPlayer.onControllerChanged`'s surfaceID write-back are regression samples). The pattern also accepts an **alias statement** between `X = E` and the negation chain — `X = E; Y = X; X = !X; if (!X && Y.attr)` (ArkTS reuses the source-level local as a register copy), and after copy propagation the alias's right may already be the same expression (`Y = E`). - **`label_x: ;` + `xpanda_goto(label_x)` is the findFollowLatch fallback and must be restored to `while (true)` first** (`GotoLoopRestore`, at the head of `SimplifyExport.simplify`): when `determineFollowLatch` can't pin down follow/latch (typically a `while (true)` whose loop head has no edge out of the loop and whose only exits are return/throw, e.g. `SabrOfflineDownloader.dumpDualTrack`, `bytebuffer.fromDebug`, `SVGRenderer.renderSwitchChild`) it inserts a goto for the back edge. The AST-side `NodeUtils.tryFixGoto` can only wrap when the label sits in the same statement block as the goto, so a goto inside a deep if branch prints `xpanda_goto(...)` — not executable. Since the label always marks a loop head, "the statements after the label to the end of that block" is the loop body: replace the gotos with `continue` and wrap it in `while (true)`. **When the body can fall through its end, append a `break;`** — the original fall-through just continues with the statements after the block, and a bare wrap would loop forever:

  ```
  label: A; if (c) goto label; B
    =>  while (true) { A; if (c) continue; break; } B
  ```

  `buildSpan` therefore records `fallsThrough` (`!terminatesInLoop(lastStatement)`) and `applySpan` pushes a `breakStatement()` after the goto replacement (`amcl1.0.6.abc`'s r2/l3 `#loadLive` events-trim loop and the four `pages/McGamePage` gotos). - **Shared return tails explode when region reduction has no goto** (`TailMergeSimplify`): a Tail with many predecessors is inlined once per predecessor (`reduceIfRegion` case 4 / `virtualizeIrregularExits` INLINE); nested region references multiply that factor (`ChannelInfoService.extractAvatarUrl`'s metadata fallback was emitted 49 times, 1029 output lines for one class). The AST-level fix is duplicate trailing block elimination: when the trailing statements of an if/else block branch are textually identical to the statements that execute right after the branch, drop the branch copy and let control fall into the outer copy. "Right after the branch" follows control flow across enclosing block/if boundaries (`continuationAfter`), stopping at loop bodies (falling off loops back), catch/finally, switch cases (fall through to the next case) and function bodies. **The merged suffix must end in return/throw/break/continue**: only then does the original path leave the enclosing structure at the copy, so the outer copy is not executed twice. Suffixes containing declarations, or identifiers declared by the branch itself, are skipped. - **Liveness must only count reads that happen before a definite write inside the same statement** (`collectReadsBeforeDefiniteWrite`): statement-granular read sets make `return v5 && (v7 = this.asRecord(...)) && v7.avatar ? ...` look like a use of the pre-statement `v7 = this.asRecord` register preload, so those dead stores never get removed. The collector walks in evaluation order: sequence elements in order; `&&`/`||` left executes first and its writes are visible to the right (the right only runs when the left completed), while the right's writes are not definite afterwards; conditional branches each see the test's writes but their own writes are not definite; blocks/if statements recurse (branch writes count as definite only when both branches write). This ordering-aware read set is used **only in the tail `cleanupDeadStores` round** (`ctx.aggressiveCleanup`): using it in every fixed-point round changes copy-propagation/condition-fold trajectories and regresses unrelated classes (`DeepLinkResolver`'s `A && (f(), A)` chains). The tail round may also drop branch live-ins that the test definitely writes on the branch's taken path (`writesOnTakenPath`), which removes the remaining register preloads. A dead store whose right-hand side is an object/array literal is kept as-is: the literal still has to be evaluated, and a bare `({...});` / `[...];` statement is not readable output. **A pseudo-goto break is not a real break**: `virtualizeIrregularExits` renders a goto as `break; //from goto label_x` (see `statements.ts`), so `transfer` must use the live set **at the label** (`ctx.labels` / `ctx.labelLive`, recorded when the reverse walk reaches the `LabeledStatement`) instead of the loop's `breakLive` — otherwise an initialization that is only read after the label (a12's `v30 = ""` before the loop, read by `v30.length` after the close/label) is deleted as a dead store while the loop's fall-through path still needs it.
- **Boolean-position test sequences carry self-negation materialization** (`ConditionSimplify.foldSelfNegationTail` / `dropTrailingValueRead`): `(v7 = acc, acc = acc, acc = !acc, !acc)` is the compiler's materialized branch polarity; the sequence value is only used for truthiness (if/ternary test, `&&`/`||` operands, `!`), so when the element just before the negation run is `X = E` (the assignment value is X's new value) or `Y = X`, the whole `X = !X, !X` run can be deleted — X's final value only changes from `!E` to `E` (same truthiness), which requires it to be dead after the statement, not captured, and not read later in the test/branches. Trailing redundant reads (`..., X = E, X` / `..., Y = X, X`) are value-exact and can always be dropped. These rules are part of `foldMaterializedTestArtifacts` (runs in the fixed-point iteration, mid-tail and at the very end); the "is it read later before a write" checks must use the anchor-aware `readsNameBeforeWriteAfterAnchor`, not `testReadsNameAfter` (later `&&` operands usually write the accumulator before reading it).

- **Value analysis (`ValueAnalysis`, reaching definitions over the CFG)**: the bytecode reuses registers heavily (`v6` is both the hole sentinel and a read buffer), so name-level checks cannot tell value versions apart. `ValueAnalysis` (in `decompiler/ValueAnalysis.ts`) computes, per basic block and register, the set of reaching definitions (normal edges only; exception landing pads have no normal predecessor, so their in-set stays empty = "unknown" and must be treated conservatively), and answers "which definition does this read see" (`definitionsAtRead`) and "who reads this definition" (`readersOf`, `isReadOutside`). `instructionAccess` collects the explicit register operands (destObj / srcObj / loadParam / params / callParams / …); `acc` is just another register. First consumer: the finally **guard** match in `buildFinallyPlans` falls back to `guardComparesSavedValue` when the syntactic `comparesHoleWith` check fails (a register copied in another block, or a guard reading a φ of {hole, exception}); on amcl this fires nowhere (the syntactic check already covers those), so the sample output is byte-identical — it is the base for the next steps. **What it is not (yet)**: the `suppress` decision is still all-or-nothing. Measuring "the end block's writes have no reader outside `[cleanupStartPC, guardEndPC]`" is wrong (237/268 amcl plans have such readers: the restored registers feed the code after the finally), and wiring `catchUsesException` to `readersOf` changed 7 classes with mixed quality (`s5` duplicated `new Error`, `v12` nested copies), so it was reverted. **The loop-tail finally layout** (`FinallyPlan.tailCleanupRange`, 13.0.1.0 only — on 24+ the registered finally handler is folded by `foldEagerCatchToFinally`, and taking it here nests an extra try/catch, hx360e `LogExport`): when the cleanup/guard are folded into the do-while test, the guard's non-throw edge is a **back edge** (`afterBranch.getStartPC() <= tryBlock.startPC`, accepted only when the guard is the *first* hole block — a register-matched guard that lands on a back edge belongs to another finally) and the cleanup copy sits in the loop body tail. The copy is sliced by instruction pc (`[endPC, guardStartPC)`, statements without a pc created by region reduction included), `applyTailCleanupFinally` wraps the statements between the start marker and the copy in `try/finally` and leaves the loop test scaffolding in place. Such a plan registers **no roles at all** (no start marker, no suppress/cleanup/guard/end) and is excluded from `classifyTryEntries`' `finallyPlans` — it has no suppress block, so a failed plan must leave the AST untouched; the start is located by `locateTryStartByPC`. Two additional rules keep it from perturbing other methods: a plan that cannot be located is removed from the failure set (the `try/finally not restored` note is itself a statement that changes the method tail and perturbs simplify — that was the `h1/q1` / `launch/c15` churn), and eager plans must stay in `classifyTryEntries`' `finallyPlans` (their start pc still marks "this try has a finally", which decides whether a shared-start user catch or the finally epilogue is kept; filtering them made `LogExport` keep both). Samples: amcl l8 `q776` `try { stat; CRC } finally { close(opened) }` (the sentinel write `v37 = hole` stays inside the finally, the loop test reads it afterwards). **A third loop shape keeps the guard as a statement group at the loop body tail** (`FinallyPlan.loopTailGuard`, 13.0.1.0 only): `for (const p of parts) { let inp = null; try { inp = open(p); while (…) read/write } finally { if (inp) close(inp) } }` compiles to `do { …; try body; CLEANUP; <spills + hole compare> } while (!guard)`, where the guard's non-throw branch is a **bare `jmp` block** (one instruction) whose destination is `<= tryBlock.startPC` (the loop head) and the sentinel comparison is materialized into the do-while test. Nothing follows the guard (no `if`, no end marker), so every classic layout fails with `no usable end marker` and the loop test silently swallows the rethrow — the inner finally disappears and an exception ends the loop as if it had finished (amcl i15 `concatParts`, whose `close(inp)` stayed a plain statement and whose exception path exited the for-of). `buildFinallyPlans` keeps the classic roles and only flags the plan; `applyLoopTailGuardFinally` wraps `[tryStart, cleanup)` in `try/finally`, drops everything from the guard marker to the end of the body list (pure guard scaffolding: register spills + the sentinel compare) and sets the loop test to `true` (the back edge is now unconditional; the only exit is the `if (done) break` inside). Gates: legacy bytecode, guard is the first hole block, and the after-branch block contains **only** the `jmp` — a loop-increment block (`mov/lda/++/jmp`) means real body code follows and the plan must keep falling through to the classic layouts (amcl `e4/a9&` `stage` lost its `try/finally` when this gate was missing) — plus AST-side checks (cleanup and guard in the same list, that list is a while/do-while body, test is `X` / `!X`). The post-loop sentinel rethrow (`acc = pending; throw acc`) is left to the enclosing plan's `applyLoopExhaustedFinally`, which is what removes it in i15.
- **A finally whose cleanup the compiler already inlined before the exit** (`FinallyPlan.eagerCleanup`): when the try's normal path ends in `return`, ArkTS inlines the cleanup before it and the exception path's handler starts with `sta` plus the await-resume dispatch, so the handler entry has two normal successors and no hole-writing suppress block exists. `buildFinallyPlans` accepts that shape (`endBlock === handlerBlock` + `jumpEqual`/`jumpNotEqual`; the cleanup is the fallthrough successor), and locates the **inlined copy** by instruction shape: the shared cleanup block's opcode/operand sequence (with pool indexes and register numbers normalised, `instructionShape`) is matched against the window of blocks that ends at the try's `return`, walking back over single-predecessor blocks (the cleanup and the return may be split into adjacent blocks). - **A try with several exits gets one inlined cleanup copy per `return`** (`locateInlinedCleanupCopies` → `applyMultiExitEagerCleanup`): `if (cancelled) return A; …; return B` compiles to a cleanup copy before *each* exit, and structured reduction nests them in the branch tails (e.g. `if (c) { CLEANUP; return A } else { …; CLEANUP; return B }`), so the single-copy layout sees no copy in the try's own statement list. The plan now stores every copy's pc range (`inlinedCleanupCopies`); the multi-exit layout wraps the whole tail of the start list in `try/finally` (reusing one copy as the finally body) and removes all copies, which is exactly the source shape (returns run the finally). Gates: every copy must map to exactly one region-built `try { CLEANUP } catch {}` wrapper (the wrapper has no instruction pc; its first body statement's pc must equal the copy start), all copies must generate identical code, and the last statement of the wrapped list must always leave the structure (`return`/`throw`/`break`/`continue`, or an if whose both branches do) — otherwise statements after the try would be swallowed into it. - **A zero-size handler whose entry is only `sta` and whose body starts in the next block is a real user catch** (`handlerBodyHasVisibleWork`), and `decideProtectedEnd` must cut its protected range at the try-table end too — otherwise the whole rest of the method is reduced into the try body and the catch swallows code the source does not protect (amcl `e4/k9 commit`: `this.revision` and the old-payload cleanup loop are outside the pending-write try; y12's download catch must stop after `createAndWait`). - **`X = []; X[0] = …` can become adjacent only after the tail structure rewrites**: `foldNextReadAssignments` inlines the last temporary element into `X[0]` after the fixed-point iteration, long after `SyntaxRewriteSimplify`'s `foldArrayAssignments` stopped running, so the array literal and the outer `obj.field = X` never merge (y12 `saveImageUrl`'s `files` field regressed to `v5 = { files: null }; v6 = [{…}]; v5.files = v6`). `SimplifyExport` therefore runs `SyntaxRewriteSimplify.foldArrayLiterals` + a second `TempVariableSimplify.foldNextReadAssignments` right before the final `ObjectLiteralSimplify`; the array elements are pure relative to the merged position (only adjacent `X[k]` assignments, no self-reference), so the fold preserves evaluation order. Sample blast radius on amcl (-j 6): 46 classes, only expression-level folds (array literals, dead temp inlining, constant-prefix hoisting) plus the y12/k9 try-range narrowing.
- **A user catch whose body tail carries the finally cleanup** (`applyPlans`' handler-tail layout): when `try { … } catch { … }` and `try { … } finally { … }` share a start, region reduction merges the normal-completion cleanup/guard into the catch body, so the cleanup marker lands in the handler list with real catch statements before it (`cleanup > 0`). The plain "handler is already the finally" layout (v24's `try { … } catch (acc) { cleanup; guard }`) must only fire when everything before the cleanup is wiring (`acc = catchAcc`, markers, register moves) — `isHandlerWiring`. Otherwise the catch is truncated at the cleanup, `[cleanup marker, guard marker)` becomes the same try's `finally`, and the statements after the guard move to right after the `try/catch/finally`; the try body's normal path then runs the cleanup through the finally, and the catch keeps its own body. amcl i15 `downloadCatalogArchive` is the sample: before the distinction the user catch was replaced by a bare `try/finally` and the warn/cleanup code vanished.
- **A finally folded into a loop's exhausted branch** (`applyLoopExhaustedFinally`, tried after the folded layout fails): ArkTS puts the code that follows a `for…of` into the loop's done branch, so `try { … for (…) { … } jarActive(); } finally { cleanup }` reduces to `do { … if (done) { <post-loop>; CLEANUP; GUARD } … } while (…)` followed by `acc = saveRegister; throw acc` — the compiler's `throw hole` "jump to cleanup" marker. When `plan.endIsMethodTail` holds (the guard's normal branch is just the implicit `return undefined`) and the done branch is the `if` that the loop body directly wraps, the layout replaces the branch tail with `break`, drops the sentinel `throw` together with the register restores before it, and wraps `[tryStart, …]` in a real `try/finally`; the cleanup segment `[cleanup marker, guard marker)` becomes the finally body and the guard scaffolding (`if (hole == sentinel) return; throw sentinel`) disappears with it. When the plan is not the method tail (`!endIsMethodTail`, i.e. the guard's non-throw branch carries real code), the continuation after the end marker is extracted from that branch (`extractGuardContinuation`, must be `fromEndMarker` and contain no declarations) and re-inserted after the new `try/finally` — amcl n16 `migrateHistory_` becomes `try { while (true) { … if (done) break; … } } finally { this.deferHistoricalCandidates_ = false; } await this.drain_(); this.hooks_.changed(); return undefined;`.
- **A finally whose cleanup/guard sit right after the loop** (`applyLoopFollowedByCleanup`): `try { while (…) { … } } finally { cleanup }` compiles to the loop, then the cleanup + guard scaffolding in the **same statement list** after it (the normal-completion path), with the try start marker inside the loop-head `if` test. `startList` is the loop body, so the loop is its parent, not an element, and `applyLoopExhaustedFinally` bails (it expects the cleanup inside the loop's done branch). The layout wraps the loop itself (`try { loop } finally { [cleanup, guard) }`) in the loop's parent list, requires the cleanup marker immediately after the loop and the guard `if` to be the list tail, and drops the implicit tail continuation (non-tail plans extract it from the guard's non-throw branch like the n16 variant). Sample: amcl n4/o8 `#~@0>#drain` (the cleanup itself is conditional: `if (v5 != undefined) this.draining = false`), whole-class snapshot `packages/xpanda-core/test/expected/amcl-n4-o8.js`.
- **v24's finally guard puts the normal continuation in the else branch**: `if (sentinel != hole) { throw sentinel } else { <continuation> }`. `applyFinallyPlans` must move that continuation back after the new `try/finally` (`extractGuardContinuation`). Dropping the whole guard deletes the code after the try/finally (`exportLogs`' success return was lost). `plan.endIsMethodTail` (`isImplicitMethodTail`) suppresses re-appending the implicit `return undefined` of the method tail. - **v24 async single-level `try { … } catch { … } finally { … }`** (`applyHandlerWrappedCatchFinally`, lnga 1.2.6 `startQrLoginScan` / `fetchThreadInfo` / `importEncryptedCredential` / `loadMorePrivateMessages`): the finally handler is emitted as an inner try/catch **inside the user-catch try body** (`try { try { body } catch { C_MARKER; cleanup; G_MARKER; sentinel compare; if (pending != hole) { throw } else { END; tail } } } catch { user }`), while the shared cleanup/guard tail is also **region-copy expanded onto the normal path right after the try/catch**; `locateMarker` resolves the plan's marker object to the *last emitted* copy (the normal-path one), so every handler-based layout mismatches (`cleanup not right after the try/catch`). Cleanup may be an expression marker structured into a condition test (`if ((C_MARKER, …, flag == undefined) && …) { cleanup }`), in which case the **whole containing statement** belongs to the finally (`inExpression` semantics). The layout merges `inner.block` + `outer.handler` into one try/catch/finally, takes `[cleanup marker, guard marker)` (statement- or expression-marked) as the finally body, and deletes the normal-path duplicate from its cleanup marker through the guard `if` carrying the `end` marker in its else; the sentinel write disappears with the guard, so the `if (flag == undefined)` cleanup wrapper folds away in simplify. Gates: `innerTry` is the **sole** statement of `outerTry.block.body`, both copies of the cleanup render identically, guard-if within a few statements after its marker and contains the end marker, no declarations in the finally body. **Non-tail plans** (`restoreContinuation` without `endIsMethodTail`, e.g. amcl `g10 checkAccount`): the guard's non-throw branch is the continuation after the try/finally — it is extracted from the main-list guard copy (the 24+ `if (pending != hole) { throw } else { END; continuation }` form via `extractGuardContinuation`, or `if (pending == hole) { CONTINUATION } throw pending` where the following `throw` is removed too), must be non-empty and declaration-free (it moves out of the guard branch into the parent list), and is re-inserted right after the merged `try/catch/finally`.  **The layout call sits in the branch condition (like `applyLoopFollowedByCleanup`), never `break left`**: zhihu `NotificationState.fetchPage` (13.0.1.0, a normal try/catch/finally) matches the same outer predicate, and a consuming branch would shadow the later layout that restores it (`try 未覆盖整个方法体` regression); conversely, inserting the branch **after** the `cleanup not right after the try/catch` branch makes that branch's `break left` win and the lnga plans die there. Order matters: put speculative layouts in the predicate, before the consuming branches whose predicates overlap.
- **`try { do { … } while (cond) } finally { … }` with the exit guard in the loop body** (`applyLoopExitGuardFinally`, lnga `SocialListSettings.runFavoritesSyncLoop`): region reduction leaves `while (true) { try { <body>; if (!cond) { cleanup; sentinel guard; return } } catch { exception save; cleanup; guard } }` — the finally handler became the try's catch, and the exit branch carries a second copy of the cleanup plus the leaked `if (hole == pending) return; throw pending`. A plain branch-3 wrap (`handler is already the finally`) would put the finally inside the loop (cleanup once per iteration, exit path still crashes on `hole`). The layout takes the handler copy's `[cleanup marker, guard marker)` as the finally body, requires the exit branch's copy to render identically (starting at the cleanup marker, ending with an `end`-marker guard `if`), replaces the whole branch with `break`, unwraps the try, and rewrites `while (true) { BODY; if (T) break }` into `do { BODY } while (!T)` before wrapping the loop in `try/finally` — the finally then runs once after the loop, exactly the source. Gates: the loop test is literal `true`, the try is the loop body's **only** statement, `plan.endIsMethodTail`, and **no `continue` bound to this loop** (a `continue` in a do-while evaluates the test, in `while (true)` it jumps straight to the head). The layout call is in the branch condition, placed before the plain handler-is-finally branch whose predicate it shares.
- **Anonymous function expressions' entry self-reference can't be deleted wholesale**: `ReservedIdentifierSimplifier` deletes `panda_jmp0_reserved_param_p0` statements as "anonymous functions have no own name"; but the entry instruction gets folded by structured reduction into the `if ((v0 = p0, ..., cond)) { whole function body }` test sequence, and deleting the statement deletes the function body too (empty function). - **Sendable classes (`callruntime.definesendableclass`) need their own slot/field handling**: the instruction is mapped to `defineClassWithBuffer` and carries the class record name as its constructor method name (`method:"SendableStandardMessageCodec"`, no `#` prefix), so the class expression is named correctly; the sendable literal's trailing nested literal is a **field name + SharedFieldType mask** table (NUMBER=1/STRING=2/BOOLEAN=4/SENDABLE=8/BIG_INT=16/GENERIC=32/NULL=64/UNDEFINED=128), not initializers — render bare class fields (`handler;`) instead of `handler = 32;` (the real assignments live in the constructor / `static_initializer`). Sendable classes get a real `@Sendable` class decorator (the `"use sendable"` constructor marker is a compiler hint and gets optimized away), and `foldExportDeclarations` must **skip export inlining for decorated declarations**: `export default @dec class {}` / `export @dec class {}` are not valid decorator positions, so the class declaration stays and `export default Name;` / `export { Name };` is kept as its own statement (`NodeFactory.parse` enables the `decorators` plugin with `decoratorsBeforeExport: true`). `newLexEnv`/`popLexEnv`/`stlexvar`/`ldlexvar` and `newsendableenv`/`stsendablevar`/`ldsendablevar` are **two independent runtime chains**: `PandaLexical` keeps them in one ordered stack but tags each entry (`lexical`/`sendable`) and resolves `lexLevel` only within the matching chain, otherwise a `stlexvar` after `newsendableenv` lands on the sendable env and two classes (one regular, one sendable) share the same slot name — the later definition silently overwrites the earlier one (`BackgroundBasicMessageChannel`'s `IncomingReplyHandler` / `IncomingSendableMessageHandler`). `sendable_<depth>_<index>` slot names must be recognized by `isTempName` (same as `local_`), otherwise `foldModuleClassDeclarations` treats `sendable_0_0 = acc` as the module target, renames the class to the slot name and orphans the real module binding (`SendableStandardMessageCodec` once decompiled to `class sendable_0_0` + `export default acc;`). Alias reads inside **function bodies** are deferred execution (methods run after module init) and may be renamed to the class binding, but reads in immediately executed top-level code must still reject the fold (`countImmediateRefsOutside`); renaming is binding-aware and anchored on the alias declarator (it may live in a lexenv block).
- **Lexical environments must propagate as stacks over the CFG, and every environment instance needs a unique name**: in a loop body, `popLexEnv` may appear earlier in pc order than other branches of the same scope, and linear scanning would name later `ldlexvar`s `local_-1_x` (undeclared variable). `PandaLexical.computeEnvStacks` propagates each basic block's **environment stack** from the entry along edges; exception handlers are seeded with the stack at the try start (exception edges aren't in the CFG; there may be `newLexEnv` between the start and the block head, use `stackAfterPC`), and the handler subgraph may contain nested tries, so seeding and propagation alternate until no new handler can be seeded. Variable names can't be just `local_<depth>_<index>`: multiple environments at the same level (typically each class's own self-reference environment for consecutively defined classes — ArkTS opens a separate lexenv per class and stores the class with `stlexvar 0,0`) would generate duplicate names, later `let`s would shadow earlier references in the block, and the optimizer would delete the outer declaration as unused (`HttpDownloader`'s `local_1_0` was once lost entirely). Now slots of the same `newLexEnv` share the prefix `local_<depth>` / `local_<depth>_<n>`, `loadLex/storeLex` resolve to the target environment's prefix via the environment stack; temp variable regexes all allow a third numeric suffix.
- `popLexEnv` may be structured into a condition test's `SequenceExpression` (the region reducer put the block that closes the scope into the `if` test). It only closes a lexical scope by splitting the enclosing block at the `panda_jmp0_reserved_lex_begin` marker, so the handle must skip that step when `node` is not a `BlockStatement` / `Program`: environment instance names are already unique, while calling `covert2SingleBlock` on a sequence reads `node.body` and throws `TypeError`, which used to drop the whole method to `SimpleAnalysis` (amcl commons/h1/w1 `#*#w91`).
- **Declaration cleanup can't trust stale `ctx.infos.refs` alone**: copy propagation clones expressions, and cloned reads aren't in refs; with `refs.size === 0` it might delete a still-referenced declaration (`RangeProxy`'s `local_1_2_1`). `removeUnusedDeclarations` also counts name occurrences over the current AST (skipping nested functions; variables captured by closures are protected by `captured`) and only deletes when truly only the declaration itself remains.
- **Catch parameters must not be named `acc`**: the handlers structured analysis generates are written against the Panda accumulator — the exception enters in `acc`, and the try body also uses `acc` as its accumulator. `catch (acc)` would shadow the function-level accumulator, and the optimizer would only see assignments to the catch parameter (`catchAcc = ...` dead chains). Now `NodeFactory.tryStatementNode` uses a separate `catchAcc`, and `TryCatchPandaStatement` inserts `acc = catchAcc` at the handler start to move the exception back into the accumulator, so later accumulator chains fold as normal `acc`.

- **Never use CommonJS `require()` in core sources** (including "lazy" requires added to dodge cycles): xpanda-web loads core TS sources directly through Vite/Rollup, the raw `require(...)` call survives bundling, and the browser has no `require` global. `PandaLexical` catches the resulting `ReferenceError` per method, so `disAssemble()` fails for every class and the web UI shows "decompile failed" / empty output while the CLI (tsx provides `require`) still works.
