# AGENTS.md

This file provides working guidance for AI coding agents in this repository.

## What This Project Is

**xpanda** — a HarmonyOS `.abc` (Panda / ArkCompiler bytecode) decompiler, implemented in **pure TypeScript** (Node.js ≥ 18). Supports bytecode version `24.0.0.0` (backward compatible with 13.0.1.0). The repo is an npm workspaces monorepo split into four sub-projects: `xpanda-core` (core library), `xpanda-cli` (command line), `xpanda-mcp` (MCP Server), and `xpanda-web` (browser UI, React + Vite, pure frontend), all under `packages/`; cli/mcp/web depend on the core library via the package name `xpanda-core`. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for architecture details.

## Requirements

- Node.js ≥ 18
- Dev dependencies: `typescript` / `tsx` / `@babel/*` / `js-yaml`, see each sub-package's `package.json` and the root `package.json` (workspaces)

## Hard Rules

1. **`packages/xpanda-core/src/disasm/opcodes.ts` is generated; do not hand-edit** — it is generated from `packages/xpanda-core/resources/isa.yaml` by `npm run gen:opcodes`.
2. File format parsing, instruction kind mapping, handle behavior, and structured reduction order must stay deterministic; validate changes with the `md5.abc` / `class.abc` test snapshots.
3. Write comments and documentation in English, keeping the existing style (class header `@Author: jmp0`).
4. Do not introduce CI configuration or change the dependency structure unless the user asks.
5. Optimizer passes return a `boolean` indicating whether the AST was modified; `SimplifyExport` runs fixed-point iteration. Do not keep procedural logs inside passes.
6. **Per-class output must be a pure function of that class**: do not introduce cross-class mutable state (global counters, mutable caches shared by offset, etc.), otherwise `-j` parallel output diverges from serial. Generated-name counters reset per class in `PandaDecompiler.decompileRaw()`; `packages/xpanda-cli/test/parallel-consistency.test.ts` has the serial/parallel consistency regression.
7. **Cross-package imports always go through package names**: cli / mcp may only import the core library via `import ... from "xpanda-core"` (single entry `src/index.ts`); no deep relative paths. core must not depend back on cli / mcp. **core must stay browser-safe**: no Node built-in modules (fs / path / os / zlib / worker_threads / Buffer, etc.) inside the import closure of the single entry, no disk IO, no workers — disk IO is implemented by cli / mcp's own `src/io.ts`, and the parallel simplify worker pool lives in xpanda-cli's `src/parallel/`.
8. **Only run `git commit` when the user explicitly asks for it.** Editing files, running tests, and reporting results never imply a commit; leave changes in the working tree.

## How To Do Common Tasks

### Add/modify a bytecode instruction

1. Check that the instruction exists in `packages/xpanda-core/resources/isa.yaml`; if not, update it and run `npm run gen:opcodes`;
2. Register the semantic kind in `KIND_MAP` / `classifyKind` in `packages/xpanda-core/src/disasm/PandaInstruction.ts` (don't forget the `InstructionKind` union);
3. If it needs dedicated semantic fields, parse them in the `PandaInstruction` constructor switch;
4. Implement a handle for that kind in `HANDLES` in `packages/xpanda-core/src/decompiler/MethodHandler.ts` (follow the existing handles' style);
5. `npm test`.

### Add a simplify pass

1. Implement `ISimplify` in `packages/xpanda-core/src/simplify/`;
2. Register it in `SimplifyExport.ts` (regular passes go into the `simplifyALL` array; global passes go at the pipeline head/tail, e.g. `CallResultSimplify`, `HighLevelGrammarSimplify`);
3. Only passes that need to run repeatedly in the fixed-point iteration go into `simplifyALL`; one-shot finishing steps (e.g. `TempVariableSimplify.foldConditionAssignments`, `SyntaxRewriteSimplify.hoistTestPrefixes`) are called directly at the end of `SimplifyExport.simplify()`;
4. Run `npm test` and confirm the snapshot changes are expected.

### Upgrade the supported bytecode version

Replace `packages/xpanda-core/resources/isa.yaml` → `npm run gen:opcodes` → add kind/semantic parsing for new instructions in `PandaInstruction.ts` → add handles in `MethodHandler.ts` → adjust format differences in `packages/xpanda-core/src/file/desc/Header.ts` etc. → `npm test` + large-sample verification.

### Modify file format parsing

The corresponding classes are in `packages/xpanda-core/src/file/`; preserve format semantics such as offset masks, cache semantics, and bounds handling. Verify with `md5.abc`, `class.abc`, and `zhihupp0.59.hap` afterwards.

### Modify the optimizer

- Copy propagation must cap expression size / clone budget to avoid `v2 = v1 + v1; v3 = v2 + v2; ...` exponential blowup;
- Cleanup of inactive variables, SequenceExpressions, return statements, and catch parameters must go through liveness / scope checks;
- **Capture detection must look at both `binding.referencePaths` and `binding.constantViolations`.** Outer variables that are "write-only" in a closure appear only in constantViolations; looking only at reads would treat the outer initialization (e.g. `local_1_1 = undefined`) as the only value, propagate it to reads after the closure, and delete the declaration;
- **Name-level liveness cannot tell old and new versions of a temp apart**: for `X = RHS` where RHS reads X exactly once, that read is the last use of the old value (`acc = p0.trim(); acc = acc.length` → `acc = p0.trim().length`). If the name is still live after the statement (later reads see the new value), a non-copyable right-hand side may only be moved into a call receiver position (`v0 = !v0.test(p0)`); the bare member load `acc = acc.test` is an intermediate form AccCallSimplify depends on — inlining it early would make `acc.call(recv, ...)` unrestorable;
- **Self-read member chains `X = X.prop; X = f(X)` → `X = f(X.prop)`** (`foldSelfReadChains`): the RHS of `X = X.prop` reads the old value, so copy propagation won't cache such expressions; if its result is consumed exactly once by the immediately following assignment, the whole expression can be moved between the two assignments. Requires A to be a pure member load, B to read X exactly once, and B to not write X or any name A depends on;
- **Accumulator chains are not limited to binary ops** (`tryFoldAccumulatorPair`): member-call/member-load chains like `X = E; X = X.trim()` / `X = X.length` also read the old value exactly once. When the read lands in the leftmost evaluation position (call receiver / member object), E may contain calls; otherwise E must be pure (evaluation order would jump over E's side effects); keep checks like `countReadsInNode === 1` and `hasDeferredSelfReference`;
- **Hub alias folding must redirect reads of the old value too** (`tryFoldTempAlias` + `redirectReadsUntilWrite`): in `acc = E; v5 = acc; <reads of acc>...; acc = G`, all reads between `v5 = acc` and the next write to acc belong to the old value; retarget them to v5 first, then move E into v5. Give up on conditional writes in branches/loops/exception paths (or writes to the target) to avoid treating post-write values as old values. Member targets (`v0.sbox = acc`) are not redirected;
- **Unfold else when the then branch always exits** (`SyntaxRewriteSimplify.flattenElseAfterExit`): `if (C) { return/throw/break/continue } else { BODY }` → `if (C) { ... } BODY`. Must run after HighLevelGrammarSimplify's ternary synthesis (if/else whose two branches are both a single return must first synthesize into a ternary, otherwise it gets torn apart), and only unfold inside statement lists (when a LabeledStatement directly wraps the if, break label depends on else staying inside the label); conservatively skip when the else block's top level has block-scoped declarations (let/const/class/function);
- **Fold boolean materialization of nested if / else-if bottom-up**: `if (!p2) { if (!f) acc = true else acc = false } else if (!g) acc = true else acc = false` should fold to `if (p2 ? !g : !f)`. `HighLevelGrammarSimplify`'s IfStatement folding uses `exit` to guarantee the inner if becomes an assignment statement first; return chains are not folded into nested ternaries, keep the `else if ... else` structure;
- **`foldShortCircuitChains` folds the `X = E; if (X/!X) { X = B; }` materialization chain into `X = E &&/|| B`** (when the test was re-materialized into the original expression by structured reduction, E must be pure). The negated form with an empty then, `if (X) {} else X = B`, is equivalent to `if (!X) { X = B }`; fold it as `X = E || B` with flipped polarity (give up when the then is non-empty or has multiple statements; only look at else when `isEmptyBranch` holds); chains starting with the self-negation `X = !X` must be skipped: the parity of the whole negation chain belongs to the tail `foldConditionAssignments`, and eating the chain head early would prevent `X = has(); X = !X; if (!X) { X = set() }` from folding back to `if (!has())`;
- **Impure expressions (`call` / `new` / functions/classes) may only move on a true last read**; when both the if's test and branch bodies read the same temp, don't move it, otherwise the call gets duplicated. **Exception**: when the read is in the if's test and both branches definitely overwrite the variable before reading it (`definitelyWritesBeforeRead`), the old value is dead after the test and may move into the test (`v0 = new RegExp(...); if (!v0.test(p0)) {...} else {...}` → `if (!new RegExp(...).test(p0))`);
- `acc = !acc` can come from `callruntime.isfalse` or from condition materialization (`istrue + jnez + ldtrue/ldfalse`); fold by the parity of the negation count, don't just strip one layer;
- Self-negation chains in test sequences (`if (A || (X = E, X = !X, !X))`) only fold when X is dead after the test, has no other reads outside the test, and branches/prefix don't read-then-write; self-negation inside loop tests is not handled yet (dead store cleanup and accumulator chain folding in loop tests are `foldLoopTestTemps`'s job, see next bullet);
- **Loop tests are expression sequences; `cleanupStatements` can't see them**: `foldLoopTestTemps` does liveness analysis in the test's own evaluation order, deleting dead stores (`acc = !(acc !== undefined)`, register restores like `v8 = false`) and folding `X = E; X = F(X)` into `X = F(E)`, `X = E; Y = X` into `Y = E`. The live set after the test must be the loop body entry live set (`loopBodyIn`, recorded by the liveness fixed-point iteration) ∪ live-after-loop (`liveAfter`): temps written-then-read inside the body (`v8.done` after `v8 = v6.call(v5)`) must not count as live uses of the test's writes; looking only at `liveAfter` would wrongly treat `v8 = false` as live;
- **A do-while's test evaluates after the body**: liveness must remove test reads where "the body definitely writes X before reading" from the loop-entry live set, otherwise `X = !E; if (!X)` won't fold (X still looks live in the loop) or would duplicate evaluation after folding. `foldDoWhileTestAssignments` then folds `do { ...; X = E } while (!X)` into `while (!E)`, requiring X dead after the loop and no `continue` in the body;
- Constant prefix hoisting like `if (A || (v1 = 0, v2 = 2, B))` (`hoistTestPrefixes`) requires: the prefix is only temps assigned constants, the short-circuit branch directly returns/throws and doesn't read those temps, and not being inside a `try` with `finally`;
- `ObjectLiteralSimplify` merges the `createobjectwithbuffer` template object with adjacent `obj.key = value`: requires field initial values to be literals, assignment order to match the template's field order, and the object not captured by closures; `obj = {...}; return obj` inlines into `return {...}` when there are no reads outside the pattern. Function properties in object literals are created in original evaluation order and are not hoisted;
- `HighLevelGrammarSimplify` synthesizes `if (x === null || x === undefined) x = default` into a switch; `NullishCoalescingSimplify` at the pipeline tail restores `v = obj.k; switch (obj.k) { case null: case undefined: v = default; }` into `v = obj.k ?? default`. Merging the two evaluations is only allowed when the discriminant is a pure member expression;
- **Switch synthesis must split out every term of the `||` test**: unrecognized terms (e.g. `!(a !== b)`, conditions with sequences) must not be silently dropped, otherwise you generate a switch that misses conditions. When the chain tail can't be split, only put the current if and its else chain wholesale into `default` (`partial`); if the very first condition can't be split, don't synthesize;
- **A for-of with early return lowered to `do { vv = it.next(); if (vv.done) return true; ... } while (test)` + `it.return()` cleanup is restored by `checkAndTransformDoWhileToForOfStatement`**: it moves the loop test to the end of the body as `if (!test) return <return value after loop>`, and constant-after-loop becomes the return after the for-of. Requires done/the after-loop return value to be boolean constants, `it` no longer read outside close, no break in the body, and continue to appear only as `if (test) continue` (guarantees the test is true on continue paths, so skipping the extra exit check is equivalent).
- **`while (true) { vv = it.next(); if (vv.done) break; vv = vv.value; ... }` is restored to `for (vv of iterable)`** (`checkAndTransformToForOfStatement`): requires `it = iterable[Symbol.iterator]()`, and `it` is not read/assigned inside the body except the first `next()` (ArkTS inlines `it.return()` in early-return branches; after the transform `it` is no longer assigned). The compiler reuses the same temp iterator/loop variable across consecutive whiles, so reads outside the loop aren't categorically forbidden: it's safe as long as a new `it = ...` / `vv = ...` definitely overwrites before the read (`hasNewerValueBefore` walks the read's ancestor blocks looking for a direct assignment; reads inside closures give up immediately). After for-of ends `vv` stays at the last element, while the while form stops at the done result object, so reads after the loop must be overwritten by later assignments; reads before the loop are unaffected. Only replace `vv.value`; other objects' `.value` in the body must stay unchanged. Decompiled AST nodes have no `start/end`, so deciding whether `vv` is inside the loop uses path ancestry (`ref.findParent`), not positions; the replacement must `.traverse` on the `body` path still attached to the AST — don't build a detached `blockStatement` and traverse it separately (missing `parentPath` breaks the scope chain of nested scopes at non-`Program` nodes, and `Scope.crawl` throws `addGlobal`);
- After changing output, update the `packages/xpanda-core/test/expected/*.js` snapshots and explain the change in the commit message.

### Modify Region Reduction / Condition Polarity

The most error-prone part of structured analysis is "should this condition be inverted":

1. **Don't rely on `regionGraph.successors()` return order**. `ValueGraph` returns in insertion order, unrelated to true/false edges; branch polarity must be decided with `edgeValueOrThrow(region, succ)`.
2. `conditionalExp` describes the fallthrough (false edge) branch condition: for jnez the false edge is `!acc`, for jeqz it's `acc`; only folding the true edge (`coalesceTailRegion`) needs `expInvert()`.
3. `simplifyConditionalSequence` merges `if (A) ... if (B) ...` into an `OrLogicalExpressionStatement` and sets `logicalRegion`; when `reduceSequence` merges such a Region it must propagate `logicalRegion`, otherwise the test can only be generated from `acc` later and the `A || B` computation is lost.
4. `Region.copy()` (irreducible Tail duplication) must preserve the `conditionalExp` / `logicalRegion` / `exceptionLandingPad` / `tryCatchHelperRegion` flags.
5. If a merged sub-region is already a `LogicalExpressionStatement` (`(A || B)` / `(A && B)`), **do not append `acc`/`!acc` again**: its expression is already the condition value; appending would overwrite the condition with the last comparison result in `acc` (`name === A || ((name === B, acc) || ...)` is both a semantic error and leaves a dead `(acc = E, !E)` assignment). `||`'s operands are jump conditions, `&&`'s operands are fallthrough conditions; invert when parent/child types differ.
6. When `virtualizeIrregularExits` hits irregular exits inside a loop body, **emit exactly one statement per edge**: conditional regions emit `if (cond) break`, linear regions emit an unconditional `break`. Emitting both yields `if (cond) break` followed by an unconditional `break`, so the body only ever runs once (`AppUpdateClient.fetchReleaseDetail`'s inner for...of once returned the iterator result object directly because of this). When the exit target is a Tail with `outDegree === 0` (only `return`/`throw` left), `break` won't do (it only jumps to the loop follow); copy the Tail's statements into that branch instead — this is exactly the case where the target has other predecessors and cannot merge.
7. **`tryCatchHelperRegion` is only valid while both try/catch branches are unconsumed**: after `reduceIfRegion` emits an `IfPandaStatement` (case 3/4) or `reduceTryCatchWithDeadBranch`, the flag must be cleared (`region.tryCatchHelperRegion = false`). Otherwise when that region keeps absorbing following code, `reduceSequence` propagates the flag all the way down, and later normal conditional regions get treated as try/catch by `IfPandaStatement`, emitting semantically wrong `try { ... } catch { success path }` statements (`HttpDownloader.request` once put its success path into catch this way).
8. **When one branch of a try/catch reduces to a Tail with `outDegree === 0` and the other is a back edge**, `reduceTryCatchWithDeadBranch` is needed: case 3 requires both branches to converge on the same successor, case 4 requires both to be Tails; when neither holds, the region graph stalls until `can not reduce the graph` (`HttpDownloader.request` / `postBinaryWithRetry` loop bodies). The continuing branch must already be reduced to `Linear` (otherwise leave it for the next fixed-point iteration), and both branches must have the current region as their only predecessor.
9. **The `&&`-merged logical region (`AndLogicalExpressionStatement`) expression is the fallthrough condition**, not the true edge condition; when folding a Tail on the true edge in `coalesceTailRegion` / `virtualizeIrregularExits`, `expInvert()` has no effect on it — use the inverted branch instead (`new IfPandaStatement(region, null, tail)`), then `normalizeConditionTests` folds it into `!A || !B`. Otherwise conditions come out inverted (`if (code && code >= 400) return` ← should be `if (!code || code < 400) return`).
10. Verify with `zhihupp0.59.hap`'s `AbsoluteUrlParser` / `ZhihuHttpClient`, `AppDestination.shouldReloadAfterAuthentication` (a 17-term `===` `||` chain), `AppUpdateClient.fetchReleaseDetail` (early return inside for...of), `yourpipe0.7.0.abc`'s `HttpDownloader.request` / `postBinaryWithRetry` (try/catch nested in the loop body), and `aes.abc`'s `Counter.increment` (must be `!== 255`).

## Pitfalls and Notes

- **Degradation paths are by design, not bugs**: single methods > 500 basic blocks and unregistered instruction kinds both route the method through `SimpleAnalysis` linear output; `jeq/jne/jstricteq/jnstricteq` instructions throw on construction, and the lexical phase (`PandaLexical`) skips the method and emits a placeholder function body without interrupting the whole class.
- Prefix instructions take 2 bytes (first byte ≥ 251) and `PandaDisAssembler` handles them specially; new instruction names (kind mapping) use the first word of isa.yaml's `sig` (e.g. `wide.callrange`).
- Class names look like `Lpkg/Name;`; they are demangled by cli / mcp's `saveClassFile()` before writing to disk (`Lpkg/Name;` → `outDir/pkg/Name.js`).
- `--no-simplify` skips the optimizer, good for validating parsing/disassembly changes; full optimization time on large files comes mostly from per-method analysis and fixed-point iteration per class.
- `acc` is the Panda accumulator, not a source variable: `acc = !acc` can come from `callruntime.isfalse` or from the compiler's boolean materialization of conditions; when both stack up it looks like two negations but the source may have only one `!`.
- `HighLevelGrammarSimplify` synthesizes `if (!X) { X = true } else { X = false }` into `X = !X`, which can form a new consecutive negation chain with an existing `X = !X`; therefore `TempVariableSimplify.foldConditionAssignments` must run once more at the pipeline tail — don't remove that step.
- The optimizer runs `TempVariableSimplify.foldAccumulatorAssignments` once before HighLevelGrammarSimplify (accumulator chains only, full-depth recursion): right-hand sides longer than `MAX_PROPAGATED_SIZE` never enter the copy propagation environment (`define` rejects them directly), so a nested accumulator chain `acc = S; acc = acc + E + F > 0` stays verbatim until the fixed-point iteration ends, making ternary synthesis fail to match `if (C) { acc = S; acc = acc + E + F > 0 } else { acc = false }` (it requires branches to be a single assignment statement).
- The optimizer tail order is fixed: HighLevelGrammarSimplify → foldShortCircuitAssignments (folds `X = E; if (E) { X = B }` newly exposed by HighLevel) → NullishCoalescing → `AccCallSimplify.simplifySequences` (restores `acc = acc.method; acc = acc.call(recv, ...)` which only exists in conditional `SequenceExpression`s; handling earlier would let later alias propagation read the wrong version) → ConditionSimplify.foldMaterializedTestArtifacts (cleans test-sequence materialization residue) → flattenElseAfterExit (unfolds else into guard clauses when the then branch exits) → foldReturnAssignments (first folds accumulator chains `X = E; X = X op F` (including member calls), then `X = E; Y = X` / `obj.k = X` (X dead, or old-value reads redirectable to Y) and last-read call arguments `X = E; f(X)` → `f(E)`, then `X = E; return X` / `X = E; return X op F`; ternary synthesis happens after the fixed-point iteration; accumulator chains must fold before alias folding, otherwise an orphaned `acc = C ? A : B` dead store remains) → foldConditionAssignments → normalizeConditionTests → foldConditionAssignments (folds the `X = Y && Z` boolean alias chains and dead stores normalize just unfolded) → normalizeConditionTests (normalizes `!(!A && !B)` into `||`) → hoistTestPrefixes → foldCompoundAssignments → `HighLevelGrammarSimplify.simplifyTail` (see next bullet). Before reordering, confirm condition polarity, compound assignment, and `test` sequence folding don't overwrite each other.
- **`matchConditionPattern`'s compound test supports multiple reads, but only when a negation chain exists**: the compiler lowers `A && (f(), A)` ("reading the same materialized boolean") into `acc = E; acc = !acc; if (!acc && (f(), acc))`; both reads in the test must be replaced with the same parity value to eliminate `acc = !acc` (`AppUpdateClient`'s `fetchReleaseDetail` guard and `AVPlayer.onControllerChanged`'s surfaceID write-back are regression samples). Constraints: E must be pure (multiple reads = multiple evaluations), the test sequence must not reassign X (the two reads in `acc = trim(), acc = acc.length, acc === 0` are different versions; replacing both with the pattern RHS is a semantic error), and multi-reads with negations = 0 stay untouched (folding `v2 = E; if (v2 && (..., !v2 ...))` would duplicate E and worsen output). Also, E reading X (`X = X.length; if (X > 0)`) is legal: the start..ifIndex assignments are deleted wholesale, and the replacement value in the test reads exactly the pre-deletion old X.
- **Loops with a constant test + guard must be lifted to `while (COND)`** (`TempVariableSimplify.foldWhileTrueBreakGuards`): ArkTS folds `while (COND)` into `while (true) { if (!COND) break; ... }`; when the guard stays in the body, accumulator materialization inside the condition (`acc = line.trim(), acc = acc.length`) and dead stores before the guard (`acc = !(i < len)`) are neither in the statement list nor the loop test, so neither `cleanupStatements` nor `foldTestSequences` can clean them. The fold runs after `cleanupConditionAssignments` (dead stores before the guard must merge into the if test first); consecutive **pure** expression statements before the guard move into the test together and are cleaned by the same round's `foldLoopTestTemps`; De Morgan/comparison inversion is left to the tail `normalizeConditionTests`. Must skip `init; while (true) { if (!cond) break; BODY; update }` (`looksLikeForLoopLowering`) and forms whose prefix contains calls (for-of/for-in's `vv = it.next()`), otherwise for / for-of / for-in restoration will never recognize them again (aes/md5's for would degrade into while + manual increments).
- **`branchReadsNameBeforeWrite` must judge while loops by evaluation timing**: the loop test evaluates before the body each round, so give up conservatively when `collectReadNames(test)` hits the name; when the test doesn't read the name, the loop itself doesn't constitute "read-before-write", and the body still recurses in statement order (`definitelyWritesBeforeRead` first, then statement by statement). Otherwise an accumulator read inside a nested loop that writes-then-reads would be treated as the whole else branch's first read, blocking the outer `acc = !!v11; if (!acc)` condition fold (`parseVttSubtitles` regression).
- **`simplifyTail` must run after all condition folds and only does five kinds of local restoration**: ① truthy-guard ternary `x ? x.k : undefined` → `x?.k` (ArkTS's lowering of `?.` when the type system guarantees the guard value is an object or nullish; in the main traversal phase it's still an `!acc` materialization chain with the guard not yet folded back to an identifier, so it must be at the tail) ② accumulator dead hub copy folding (`acc = E; v14 = acc` with acc overwritten right after → `v14 = E`, RHS must be pure) ③ while(true)+break-form for-of restoration, including the `v21 = it; v20 = it.next; v22 = v20.call(v21)` method-quantity hoisted lowering (`foldHoistedIteratorNext` normalizes it to `v22 = it.next()` first; when the alias was inlined by earlier folds, both the `G = X[Symbol.iterator](); F = G.next` forms must be recognized); after a successful transform `tryInlineForOfIterable` inlines `X = E` that only feeds the iterator into the for-of head (the for-of head's own `of X` is also a reference to X — exclude it in the check) ④ consecutive `if (disc === v) { return ...; }` guard chains in the same statement list → `switch` (ArkTS's lowering of source switches; else-if blocks are first unfolded into guard clauses by `flattenElseAfterExit`): requires at least 3 case labels (including fallthrough labels split from `A || B`), 2-label short chains stay as ifs (the old `checkAndTransformToSwitchCase` was raised to ≥3 in sync; only null/undefined pairs keep 2 cases for `??` restoration), discriminant and case values side-effect-free, branch bodies' top level ending in return/throw (otherwise matching must keep checking later ifs, semantically not equivalent), no bare break in branch bodies that would bind to an outer loop (switch would intercept it), only `===` accepted (switch cases use strict comparison), a return/throw immediately after the chain folds into default; block-level declarations at a case body's top level get wrapped in a block ⑤ cleans up `vN`/`acc` declarations that are only the declaration itself (`removeUnusedTempDeclarations`, counted over the whole function subtree including nested functions, prefer keeping). This lowering also doesn't match the shape in the main traversal phase. After deleting statements, referencePaths in bindings aren't cleaned; `hasNewerValueBefore` skips references to the deleted `indexOf === -1` statement as "no longer executed"; references inside loops must be decided with the current AST's node set (collected by walkNode), not `findParent` — replaced/deleted nodes' parentPath chains are stale and would misjudge vanished reads as in-loop.
- **ArkTS 13 (bytecode 13.0.1.0) finally handler forms vary by compiler version**: some catch blocks have `codeSize === 0` (`RegionGraphBuilder` skips them; the handler isn't in the region graph), some carry `sta vX` saving the exception (2/3 in `yourpipe0.7.0.abc`). `TryFinally.buildFinallyPlans` must not filter by codeSize; identify by structural features: the try-exit block writes the `hole` sentinel and jumps to cleanup, the handler starts with `sta` and doesn't throw directly, and after cleanup there's an `X != hole` rethrow guard. `applyFinallyPlans` supports three layouts: try body/cleanup/guard in the same statement list; all three at the tail of nested lists; and structured analysis having already emitted the handler as `try { ... } catch (acc) { cleanup ... guard }` (the same try start has both a real catch and the finally handler) — the last one is rewritten directly into `try/finally`, discarding the sentinel save and rethrow guard wholesale. The try start / cleanup / guard may also be structured into a condition test's `SequenceExpression`; `handleBlock` marks them with expressions and `applyFinallyPlans` hoists them to the statement containing that test. When still unlocatable, it leaves `/* xpanda: try/finally not restored */` at the end of the function body — don't treat it as globally fixed.
- **Finally's reads are live at every exit of the try**: `TempVariableSimplify`'s liveness model has no exception edges, so `return/throw/break/continue` exits must be merged into `finalizerReads` (`LoopLive.finallyLive`), otherwise `v14 = request` in the try gets deleted as a dead store, finally is left with only the pre-try `v14 = null`, and the cleanup logic becomes dead code.
- **Anonymous function expressions' entry self-reference can't be deleted wholesale**: `ReservedIdentifierSimplifier` deletes `panda_jmp0_reserved_param_p0` statements as "anonymous functions have no own name"; but the entry instruction gets folded by structured reduction into the `if ((v0 = p0, ..., cond)) { whole function body }` test sequence, and deleting the statement deletes the function body too (empty function). Only delete when the whole statement is the self-reference assignment; otherwise replace the identifier with `undefined`.
- **Lexical environments must propagate as stacks over the CFG, and every environment instance needs a unique name**: in a loop body, `popLexEnv` may appear earlier in pc order than other branches of the same scope, and linear scanning would name later `ldlexvar`s `local_-1_x` (undeclared variable). `PandaLexical.computeEnvStacks` propagates each basic block's **environment stack** from the entry along edges; exception handlers are seeded with the stack at the try start (exception edges aren't in the CFG; there may be `newLexEnv` between the start and the block head, use `stackAfterPC`), and the handler subgraph may contain nested tries, so seeding and propagation alternate until no new handler can be seeded. Variable names can't be just `local_<depth>_<index>`: multiple environments at the same level (typically each class's own self-reference environment for consecutively defined classes — ArkTS opens a separate lexenv per class and stores the class with `stlexvar 0,0`) would generate duplicate names, later `let`s would shadow earlier references in the block, and the optimizer would delete the outer declaration as unused (`HttpDownloader`'s `local_1_0` was once lost entirely). Now slots of the same `newLexEnv` share the prefix `local_<depth>` / `local_<depth>_<n>`, `loadLex/storeLex` resolve to the target environment's prefix via the environment stack; temp variable regexes all allow a third numeric suffix.
- **Declaration cleanup can't trust stale `ctx.infos.refs` alone**: copy propagation clones expressions, and cloned reads aren't in refs; with `refs.size === 0` it might delete a still-referenced declaration (`RangeProxy`'s `local_1_2_1`). `removeUnusedDeclarations` also counts name occurrences over the current AST (skipping nested functions; variables captured by closures are protected by `captured`) and only deletes when truly only the declaration itself remains.
- **Catch parameters must not be named `acc`**: the handlers structured analysis generates are written against the Panda accumulator — the exception enters in `acc`, and the try body also uses `acc` as its accumulator. `catch (acc)` would shadow the function-level accumulator, and the optimizer would only see assignments to the catch parameter (`catchAcc = ...` dead chains). Now `NodeFactory.tryStatementNode` uses a separate `catchAcc`, and `TryCatchPandaStatement` inserts `acc = catchAcc` at the handler start to move the exception back into the accumulator, so later accumulator chains fold as normal `acc`.
- When testing test-sequence negation chains and condition assignment folding, prefer `zhihupp0.59.hap`'s `AbsoluteUrlParser` (`if (host.length === 0 || host.startsWith("["))`) and `aes.abc`'s `Counter.increment` (`if (arr[i] !== 255)`) as regressions.
- `NodeFactory.generate()` wraps lines over 120 characters at top-level `||` / `&&` / `??` at the end (`packages/xpanda-core/src/ast/FormatCode.ts`), with new lines starting with the operator; lines inside strings/templates/comments/regexes and lines with top-level ternaries are not wrapped. It only affects output text, not AST semantics; keep this formatting when adding snapshots.
